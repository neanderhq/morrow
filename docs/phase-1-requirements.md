# Recruiting app — Phase 1 requirements

I want to build a recruiting app for my company, similar to Greenhouse. This is Phase 1. We will build it in stages, and this first stage is the foundation: workspace, staff accounts, roles and login. Please build it as a real, working app with a database, not a mockup.

Product overview (for context, later stages will add these):
- Jobs: create, edit, publish, close and reopen job openings.
- Public careers page where candidates apply with a resume (PDF or DOCX).
- Candidates and applications that move through pipeline stages, with notes, search and filters.
- Audit trail of important actions.
- In a later phase we will add interviews, scorecards, offers and reports, so please design the data model so these can be added later without rebuilding what exists.

What I need in this stage:

1. Company workspace
- One shared workspace for my company (name, and the staff who belong to it).
- All staff data and later all jobs and candidates belong to this workspace.

2. Staff accounts and roles
- Four roles: Admin, Recruiter, Hiring Manager, Interviewer.
- The first person who sets up the workspace becomes Admin.
- Admins can invite staff by email and pick their role, change a staff member's role, and deactivate a staff member. A deactivated user cannot log in.
- If invite emails cannot be sent from this environment, show the Admin an invite link they can copy and share, and tell me clearly that this is the limitation.

3. Login and sessions
- Email and password login, logout, and sessions that survive a page refresh.
- Logging out ends the session on the server, not only in the browser.
- Password recovery: a user who forgot the password can reset it. If emails cannot be sent from this environment, tell me and propose a safe alternative (for example a reset link generated by an Admin). Do not skip this feature silently.
- Basic password rules (minimum length) and a clear error for wrong credentials.

4. Permissions enforced on the server
- Every page and every API endpoint must check the user's role on the server. Hiding a button is not enough: if someone without permission calls the API directly or opens the URL, it must be denied.
- For this stage: only Admins can see the staff management page, invite users, change roles and deactivate users. All logged-in staff can see their own profile. Logged-out users are sent to the login page.
- Please also write a simple role and permission matrix (a table: what each role can do) in the project docs, covering this stage and the planned features, so I can review it.

5. Basic layout
- A simple app shell with navigation (Dashboard, Jobs, Candidates, Staff, Profile). Jobs and Candidates can be placeholders for now.
- It must work on desktop and on mobile.

When you finish:
- Make sure the app runs in the preview with a working database, and the changes are committed and pushed.
- Tell me how to create the first Admin and how to test each role.
- List anything you could not do or any limitation (for example email sending).
