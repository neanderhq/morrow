# Data Workspace Framework

Use this guide when the project pins `attio@2.0.0`. The customer request defines the product and features. The manifest is authoritative for pack discovery, delivery, and preview resources.

This rebuild requires the project’s initialized `shadcn@1.0.0` foundation. Controls import from `@/components/ui/*`, a customer-project alias, never Neander’s renderer. `AttioButton`, fields, selects, tabs, menus, dialogs, tables and feedback compose those primitives; `AttioIcon` maps to Lucide. Pack colors and typography alias project tokens. Preserve `.neander/foundation.json`, `components.json`, global CSS, and legitimate component customizations. Never install a competing palette or regenerate the theme. Use the document root `.dark` for dark mode. The legacy `theme` prop is retained for API compatibility and does not override project tokens.

The `2.0.0` pilot scope is frozen: the core workspace/collection framework plus the previously requested workflow graph editor, report editor, structured notes, Home, and task assistant. These surfaces are available for requested compositions, not automatically enabled in customer apps. Defer additional built-in modules; use the existing custom-page content and callback extension points for customer-specific features. This pilot does not add workflow execution, report queries, AI services, or calendar integrations.

Start with the smallest requested collection and workflow. A vague CRM request uses one customer collection and its record page; do not add a dashboard or neighboring modules automatically. Other data-heavy workspaces use their own labels, fields, and actions. An omitted model feature stays hidden; a requested empty collection shows its empty state.

Import the canonical installed `AttioFramework` and its versioned CSS. Configure `AttioFrameworkModel` with requested collections, columns, tables, kanban views, record pages, and custom pages. Model an inventory, directory, registry, or other entity list as an object collection with records, columns, and a record page; do not rebuild it as a custom page with a page-local table or detail panel. Reserve custom pages for surfaces that are not collection workflows. Do not invent dashboard metrics, sample badges, or overview chrome that the customer did not request.

`AttioFramework` owns the visible application shell, including its header and collection toolbars. Render `<AttioFramework model={model} actions={actions} />` as the page; provider and routing wrappers stay visually empty. Use the collection's shared search and filter controls. Put requested extensions inside the relevant shared surface; do not add a separate heading, count strip, search, or filter bar above or beside the shell, or hide the shared toolbar with customer CSS. An additional standalone surface is appropriate only when the customer explicitly requests it.

Use `AttioFrameworkActions` for semantic intents; customer code owns data, authorization, and persistence. Let the framework own collection row selection and its overlay record drawer. Closing record details must restore the collection's full width, and opening details must not resize the table or introduce page-level horizontal scrolling. Keep pending states, recoverable errors, drafts, and confirmation after success. Use the shared tokens and components for new UI where practical; customer-specific content and legitimate extensions are welcome. Keep pack styles isolated from Neander's frontend.

Use the pack’s workspace, collection, kanban and record layouts; compose additional controls from the shared shadcn foundation. Do not copy catalog fixture data into customer output. Keep CRM-specific tasks, notes, and contact actions only when requested. Component exports and prop types are available in the staged React source.

When requested, compose `AttioWorkflowEditor` or `AttioReportEditor` in a framework `pages` entry with `layout: 'editor'`. Workflow block types, branch output ports, fields, templates, generation, settings, runs, and publishing behavior come from the host. The shared graph editor owns node positions, explicit connections, pan/zoom, selection, undo/redo, and structural/required-field feedback; applications preserve that graph in their save callback. Reports receive source choices and aggregated preview data through typed callbacks. Notes with a structured `document` open from the Notes collection as a dedicated `AttioNoteDetail` page; wire `updateNote`, `favoriteNote`, and `deleteNote` only when supported. Keep these editors absent from unrelated products. Their UI does not execute workflows or query customer data.

Run the normal build and browser walkthrough on the generated project at desktop and mobile widths. Pass the staged `evals/scenarios.json` checks and requested workflow to `ui-quality-review`; include the initial full app shell before opening a record, then inspect loading, empty, error, keyboard, and responsive states. Correct in-scope composition defects through the normal UI remediation flow before reporting completion. Record actual limitations. The catalog preview demonstrates the pack but does not verify the generated customer app.
